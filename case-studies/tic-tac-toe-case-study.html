Tic-Tac-Toe

A fully playable browser game that proves clean game logic, smooth state management, and polished UI can live entirely in vanilla JavaScript "” no framework required.

What was the brief?

Build a playable Tic-Tac-Toe game entirely in the browser "” two-player, with win detection, draw detection, turn tracking, and a reset function. Everything had to work without a framework and feel polished enough to embed in a portfolio.

This project was intentionally scoped small to prove that the fundamentals "” logic, state, and UI feedback "” can be done cleanly in vanilla JS. It's the same problem space as game development, just at a smaller scale.

What decisions did I make and why?

  • Array-based game state: The board is a 9-element array. Every click updates the array, then the entire UI re-renders from that single source of truth "” the same pattern React uses, just without the library.
  • Win detection via combinations: I preloaded all 8 winning combinations (3 rows, 3 columns, 2 diagonals) and check against the array after each move. It's O(1) "” fast regardless of how many cells exist.
  • Immutable-style updates: Rather than mutating DOM nodes directly, I clear and re-render on every state change. This eliminates a whole class of bugs where stale DOM state contradicts game state.
  • Visual win highlight: Winning cells get a distinct CSS class with a glow effect, giving the player clear and immediate feedback about why the game ended.
  • Reset without reload: Game reset wipes the state array and re-renders "” no page reload needed. This keeps the experience fluid and respects the player's time.

Tools, technologies, and what I learned

Stack used

  • Vanilla JavaScript (ES6+)
  • HTML5 and semantic markup
  • CSS for game states and animations
  • Vercel for deployment
  • aria-label attributes for accessibility

Key learnings

  • State management patterns: keeping a single source of truth and deriving all UI from it eliminates entire categories of bugs.
  • Game loop thinking: even a simple game needs a clear cycle "” input → update state → render "” and respecting that cycle keeps code maintainable.
  • The value of small projects: scoping tightly forces you to implement things correctly rather than hiding complexity behind abstractions.
  • Accessibility in interactive elements: every cell needs a proper aria-label so screen reader users know which cell they're interacting with.

What would I do differently? What am I proud of?

I would add a single-player mode with an AI opponent using the minimax algorithm "” a classic CS problem that maps directly to this game's structure. That would turn a two-player demo into a genuinely replayable experience.

I'd also add an animation when the winning line is drawn across the board "” a visual that traces the three cells "” to make the win feel more satisfying.

I'm proud of the state architecture. The code reads clearly, the logic is self-contained, and there are no hacky DOM checks scattered through the codebase. It's the kind of clean, maintainable code I want to write on every project.
